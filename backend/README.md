# OwnAI Backend

FastAPI-Backend: Auth, Chat/Agent-Loop gegen Ollama, Kalender (CalDAV), Home Assistant (Smart-Home-Steuerung), Android-Notification-Ingestion + KI-Vorschläge, Sprach-Eingabe (Whisper/Wyoming). Implementiert exakt den Vertrag aus [`../API.md`](../API.md).

Für Sprach-Transkription (`POST /voice/transcribe`) wird `ffmpeg` benötigt (im Docker-Image bereits enthalten; für lokale Entwicklung außerhalb Docker: `apt install ffmpeg` bzw. Äquivalent).

## Lokale Entwicklung

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt

cp ../.env.example .env   # dann DATABASE_URL für lokale Entwicklung anpassen, z.B.:
# DATABASE_URL=sqlite+aiosqlite:///./ownai.db

python -m alembic upgrade head
uvicorn app.main:app --reload
```

Ohne laufendes Ollama antwortet `/api/v1/health` mit `"ollama": "unreachable"` — Chat-Anfragen schlagen dann mit einem 5xx von httpx fehl, alles andere (Auth, Kalender, Geräte) funktioniert unabhängig davon.

## Tests

```bash
pip install -r requirements-dev.txt
pytest        # 27 Tests, laufen gegen eine temporäre SQLite-DB; Ollama/CalDAV/Home-Assistant sind gemockt,
              # der Wyoming/Whisper-Roundtrip läuft echt gegen einen Test-TCP-Server (kein Mock)
ruff check app tests
```

Beides lief in dieser Session tatsächlich grün (siehe Session-Zusammenfassung).

## Architektur

- `app/db/models.py` — SQLAlchemy-2.0-Modelle, dialektunabhängig gehalten (String-UUIDs, generisches JSON) — funktioniert identisch gegen SQLite (Tests/Dev) und Postgres (Prod).
- `app/agent/` — Tool-Loop: `orchestrator.py` ruft Ollama (`app/services/ollama_client.py`, natives `/api/chat` mit `tools`) auf, führt zurückgemeldete Tool-Calls über `app/agent/tools.py` aus (max. 5 Runden), persistiert am Ende eine einzelne Assistant-Message mit allen `tool_calls` (siehe `API.md`, bewusst kein Streaming in v1). `orchestrator._strip_internal_urls` entfernt vor dem Speichern jeden `/api/v1/...`-Pfad aus der finalen Antwort — lokale Modelle ignorieren die Prompt-Anweisung "nenn niemals URLs aus Tool-Ergebnissen" manchmal (z.B. geben sie nach `create_file` den rohen `download_url`-Pfad wieder) und das wäre besonders in Voice fatal (roher API-Pfad würde vorgelesen). Das ist eine harte Garantie, kein Prompt-Wunsch.
- `app/agent/skills.py` — **Skills**: pro Unterhaltung wählbarer Fokus (`Conversation.skill`, Standard `"general"`). Jeder Skill hat einen Prompt-Zusatz und optional eine feste Tool-Teilmenge (`tool_names`). `orchestrator.py` bietet dem Modell nur die Tools des aktiven Skills an (`_tools_for_skill`) UND weist serverseitig jeden Tool-Call zurück, der außerhalb davon liegt — auch wenn ein Modell sich an einen Tool-Namen aus einer früheren Runde "erinnert" und ihn trotzdem versucht. Neue Skills werden einfach im `SKILLS`-Dict ergänzt, keine Migration nötig außer beim allerersten Hinzufügen der Spalte.
- `app/agent/subagent.py` — **Sub-Agents**: `spawn_subagent`-Tool, delegiert eine Teilaufgabe an einen eigenen, kleinen Tool-Loop (max. 5 Runden, eigener System-Prompt, keine eigene Message-Persistenz). **Verschachtelung ist bei genau einer Ebene hart begrenzt**, nicht nur per Prompt-Anweisung: `run_subagent` filtert `spawn_subagent` aus der Tool-Liste, die es seinem eigenen `ollama_client.chat`-Aufruf mitgibt — der Sub-Agent kann das Tool also gar nicht sehen, geschweige denn aufrufen. Respektiert außerdem die Skill-Einschränkung der Unterhaltung (siehe oben), bekommt also nie mehr Werkzeuge als die Hauptunterhaltung selbst. Der Sub-Agent-System-Prompt weist explizit darauf hin, dass er keine Rückfrage stellen kann (es gibt niemanden, der antwortet) und stattdessen bei unterspezifizierten Aufgaben eine vernünftige Annahme treffen und diese kurz nennen soll — das war ein konkret gemeldetes Problem (Sub-Agent "hängt"/reagiert inkonsistent, weil er eigentlich auf eine Antwort wartet, die nie kommt).
- `app/services/calendar_service.py` — CalDAV via `python-caldav`, Zugangsdaten Fernet-verschlüsselt in der DB (`app/services/crypto.py`, Schlüssel von `SECRET_KEY` abgeleitet).
- `app/services/home_assistant_service.py` — Home Assistant REST-API (`GET /api/states`, `POST /api/services/{domain}/{service}`) via `httpx`. Jeder Nutzer verbindet seine **eigene** HA-Instanz (kein globales Setup) — Long-Lived-Token Fernet-verschlüsselt gespeichert, analog zu CalDAV. `ALLOWED_DOMAINS` sperrt administrative HA-Domains (`homeassistant.*`, `shell_command`, `python_script`) für das LLM-Tool, damit der Agent nur unkritische Geräte (Licht, Steckdosen, Heizung, ...) steuern kann.
- `app/services/notification_service.py` — nimmt Android-Notifications entgegen, klassifiziert sie asynchron (FastAPI `BackgroundTasks`) per LLM-Prompt zu einem strikten JSON-Urteil, legt bei Relevanz eine `NotificationSuggestion` an. Warum eine Notification *keinen* Vorschlag erzeugt hat, ist jetzt im Backend-Log sichtbar statt komplett unsichtbar: `WARNING` mit dem rohen LLM-Output, wenn das Modell kein parsebares JSON liefert (häufigster Fehlerfall bei lokalen Modellen — sie ignorieren manchmal die "nur JSON"-Anweisung), `DEBUG`, wenn schlicht `relevant=false` klassifiziert wurde. Praktisch beim Debuggen von "Suggestions zeigt nie was an": `docker compose logs backend` nach dem Senden einer Test-Nachricht durchsuchen.
- `app/mcp_servers/` — dieselbe Kalender-/Notification-Logik zusätzlich als eigenständige MCP-Server (stdio) für externe MCP-Clients (z.B. Claude Desktop), unabhängig vom internen Tool-Loop-Pfad des Chat-Endpunkts (siehe Docstrings in den Dateien, warum beide Pfade bewusst getrennt sind).
- `app/services/whisper_client.py` — Speech-to-Text über eine bestehende Wyoming-ASR-Instanz (z.B. wyoming-whisper). Kein REST-API — Wyoming ist ein eigenes Event-Protokoll über eine rohe TCP-Verbindung (Python-Paket `wyoming`, siehe [github.com/rhasspy/wyoming](https://github.com/rhasspy/wyoming)). Empfangenes Audio (WebM/Opus, MP4/AAC, ...) wird per `ffmpeg`-Subprozess zu 16kHz-Mono-PCM dekodiert (das von Wyoming erwartete Format), dann als `Transcribe`→`AudioStart`→`AudioChunk`(s)→`AudioStop`-Event-Sequenz gesendet; die Antwort ist ein `Transcript`-Event mit dem erkannten Text.
- `app/services/file_service.py` — `create_file`-Tool (siehe `app/agent/tools.py`): rendert PDF (`fpdf2`, reines Python ohne System-Libs) oder speichert Text/Markdown, pro Nutzer/Unterhaltung unter `FILES_STORAGE_DIR`. **Sicherheitsdesign**: der Dateiname auf der Platte ist immer die server-generierte UUID der DB-Row, nie der vom LLM/Nutzer gelieferte `filename` (der ist rein Anzeige/`Content-Disposition`, sanitisiert) — dadurch ist Path-Traversal über einen manipulierten Dateinamen strukturell ausgeschlossen, nicht nur validiert.
- `app/services/email_service.py` — `send_email`-Tool. Nutzt stdlib `smtplib` (in `asyncio.to_thread`, da blockierend) statt einer Async-SMTP-Bibliothek, bewusst wegen der stabileren/besser dokumentierten Standard-API. Effektive Konfiguration: eigenes verbundenes SMTP-Konto des Nutzers (`POST /integrations/email`) > `SYSTEM_SMTP_*`-Umgebungsvariablen > `409 email_not_configured`.
- `app/services/vision_service.py` — `POST /vision/describe`: `ocr_image()` (Tesseract via `pytesseract`, deterministisch, kein LLM/Netzwerk nötig) und `describe_image()` (async, nur falls `OLLAMA_VISION_MODEL` gesetzt ist — sendet das Bild base64-kodiert an Ollamas natives multimodales `/api/chat`). Beide best-effort: liefern `null` statt eines Fehlers, wenn nicht verfügbar (fehlendes `tesseract-ocr`-Systempaket bzw. kein Vision-Modell konfiguriert).
- `app/services/push_service.py` — Web Push (VAPID, `pywebpush`). `send_push()` ist der einzige Weg, wie der Assistent den Nutzer **proaktiv** kontaktiert (nicht nur auf Anfragen reagiert): pro `PushSubscription` des Nutzers ein `webpush()`-Aufruf (blockierend, daher `asyncio.to_thread`); antwortet der Browser mit `404`/`410` (Subscription abgelaufen/ungültig), wird sie automatisch entfernt. Ohne `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` ist alles ein stiller No-op (`is_push_configured()`). **Nicht live gegen einen echten Push-Dienst getestet** — ein echter `PushManager.subscribe()`-Aufruf braucht Netzwerkzugriff zu Googles/Mozillas Push-Infrastruktur, der in der Build-Sandbox dieser Session nicht verfügbar war; ein echter, dabei gefundener und gefixter Bug (`navigator.serviceWorker.ready` fehlte vor `pushManager.subscribe()`, siehe `web/src/lib/push.ts`) zeigt aber, dass der Subscribe-Flow bis dorthin lief. Vor Produktiveinsatz einmal live mit echten VAPID-Keys durchklicken.
- `app/services/agent_bus_service.py` — **Agent Bus**: der zentrale Hub, über den eigene andere Projekte/Webseiten des Nutzers (`AgentIdentity`, eigener API-Key wie bei `Device`) Freitext-Nachrichten und strukturierte Tasks austauschen (`AgentMessage`, vollständig geloggt). Pro Nutzerkonto isoliert. Der reservierte Name `"ownai"` braucht keine Registrierung und steht für den Kontobesitzer selbst — eine Nachricht dorthin löst zusätzlich `push_service.send_push()` aus, ein weiterer proaktiver Kontaktkanal neben Timern/Suggestions. Der Chat-Agent selbst kann über die Tools `agent_bus_list_agents`/`agent_bus_send_message` (`app/agent/tools.py`) im Auftrag des Nutzers am Bus teilnehmen.
- `app/services/memory_service.py` — **Gedächtnis**: kurze Fakten über den Nutzer (`UserMemory`, max. 512 Zeichen), die `orchestrator.run_turn()` vor jedem Tool-Loop lädt (`memories_for_prompt`, neueste zuerst, gedeckelt auf `MAX_MEMORIES_IN_PROMPT = 50`) und `_system_prompt()` als "Bekannte Fakten über den Nutzer"-Block in den System-Prompt einmischt — der Nutzer muss einmal genannte Fakten also nicht in jeder neuen Unterhaltung wiederholen. Fakten entstehen manuell (Settings → Gedächtnis) oder automatisch über die Tools `remember_fact`/`list_memories`/`forget_fact` (`app/agent/tools.py`), die der Agent selbstständig während des Chats aufruft.
- `app/services/contact_service.py` — **Kontakte**: `Contact`-Model (Name, optional Telefon/E-Mail/Notizen, Geburtstag als `birthday_month`/`birthday_day`/optionalem `birthday_year` statt eines einzelnen Date-Felds, weil der Scheduler nur Monat+Tag gegen "heute" matchen muss und viele Nutzer das Jahr nicht teilen wollen/kennen). `contacts_with_birthday_on()` liefert die Kandidaten für den täglichen Geburtstags-Check (siehe `scheduler.py`). Kontakte entstehen manuell (Settings → Kontakte) oder über die Tools `add_contact`/`list_contacts`/`update_contact`/`delete_contact` (`app/agent/tools.py`).
- `app/services/reminder_service.py` — **Wiederkehrende Erinnerungen**: `RecurringReminder`-Model, im Gegensatz zu `Timer` (einmaliger Countdown) dauerhaft wiederkehrend (`recurrence`: `daily`/`weekly`/`monthly`, plus `hour`/`minute` und je nach `recurrence` `weekday` oder `day_of_month`). `reminders_due_at()` liefert die Kandidaten für den minütlichen Scheduler-Poll (siehe `scheduler.py`) — matcht Stunde/Minute exakt und (je nach `recurrence`) Wochentag/Monatstag gegen den übergebenen Zeitpunkt, übersprungen wird alles mit `active=false` oder bereits heute ausgelöstem `last_triggered_date`. Erinnerungen entstehen manuell (Settings → Erinnerungen) oder über die Tools `add_reminder`/`list_reminders`/`update_reminder`/`delete_reminder` (`app/agent/tools.py`) — `update_reminder` mit `active=false` pausiert, ohne die Erinnerung zu löschen.
- `app/services/automation_service.py` — **Automatisierungen**: `Automation`-Model (`entity_id`, `trigger_state`, `message`, `active`, `last_seen_state`) — "warne mich, wenn diese HA-Entität einen bestimmten Zustand erreicht". `list_active_automations()` liefert alle aktiven Automatisierungen über alle Nutzer für den Scheduler-Poll (siehe `scheduler.py`), der sie pro Nutzer gruppiert, um pro Poll nur einen `GET /api/states`-Aufruf je Nutzer zu brauchen statt einen pro Automatisierung. Automatisierungen entstehen manuell (Settings → Automatisierungen) oder über die Tools `add_automation`/`list_automations`/`update_automation`/`delete_automation` (`app/agent/tools.py`) — der Agent nutzt dafür typischerweise vorher `home_assistant_list_entities`, um `entity_id` und mögliche Zustandswerte herauszufinden.
- `app/services/list_service.py` — **Listen**: `TodoList`/`TodoListItem`-Modelle (Todo- oder Einkaufslisten, unterschieden per `kind`), mit Einträgen als eigenständiger Kindtabelle. Named `TodoList` statt `List`, um das Builtin `list` nicht innerhalb von `app/db/models.py`s eigenen Typ-Annotationen zu überschatten. **Wichtig für den async-Pfad**: jede Rückgabe eines `TodoList`-Objekts muss dessen `items`-Relationship explizit eager laden (`selectinload(TodoList.items)` beim Query, oder `await db.refresh(todo_list, ["items"])` nach einem Insert/Update) — unter dem Async-Treiber löst ein unberührtes, lazy geladenes Relationship-Attribut beim Pydantic-Serialisieren `MissingGreenlet` aus, da implizites Lazy-Loading synchrones IO bräuchte, das der Async-Treiber nicht "nebenbei" nachliefern kann. Listen und Einträge entstehen manuell (Settings → Listen) oder über die Tools `create_list`/`list_lists`/`delete_list`/`add_list_item`/`update_list_item`/`delete_list_item` (`app/agent/tools.py`).
- `app/services/expense_service.py` — **Ausgaben-Tracker**: `Expense`-Model (`amount` als einfacher `Float`, keine Mehrwährungsunterstützung — für persönliche Summenübersichten ausreichend). Bewusst ohne Edit-Endpunkt: eine falsch eingetragene Ausgabe wird gelöscht und neu angelegt statt bearbeitet, passend zum Umfang eines schlanken Trackers statt einer vollständigen Buchhaltung. `list_expenses()` filtert optional nach Datumsbereich/Kategorie, `totals()` berechnet Summe und Kategorie-Aufschlüsselung über die (gefilterte) Liste — unkategorisierte Ausgaben laufen unter `"Sonstiges"` (`UNCATEGORIZED`-Konstante). Ausgaben entstehen manuell (Settings → Ausgaben) oder über die Tools `add_expense`/`list_expenses`/`delete_expense` (`app/agent/tools.py`).
- `app/services/searxng_service.py` — **Web-Suche**: `GET /search?q=...` über die eigene, selbst gehostete SearXNG-Instanz des Nutzers (`SearxngAccount`, nur URL, kein Token nötig — SearXNGs JSON-API ist im eigenen Netz üblicherweise unauthentifiziert, im Gegensatz zu CalDAV/HA also kein `crypto.py`-Einsatz). `_client()` ausgelagert wie bei `home_assistant_service`/`weather_service`, rein für `monkeypatch` in Tests. Fehler `SearxngNotConnected`/`SearxngError` lokal in der Datei definiert statt in `app/errors.py`, analog zu `HomeAssistantNotConnected`/`HomeAssistantError`. Nutzbar über das Tool `web_search` (`app/agent/tools.py`). **Nicht live gegen eine echte SearXNG-Instanz getestet** — kein Netzwerkzugriff in der Build-Sandbox dieser Session; die Verbinden-UI wurde live bis zum Status "Verbunden" durchgeklickt, die eigentliche Suchanfrage aber nicht. Vor Produktiveinsatz einmal mit einer echten Instanz durchklicken.
- `app/services/rss_service.py` — **News/RSS**: `RssFeed`-Model (nur `url`+optionaler `name`, keine Artikel gespeichert). Nutzt das dritte-Party-Paket `feedparser` (neu in `requirements.txt`) zum Parsen von RSS 2.0/Atom-XML — deutlich robuster gegenüber echten, teils leicht fehlerhaften Feeds als eine selbstgebaute `xml.etree`-Lösung. `add_feed()` ruft den Feed einmal ab, um `<title>` als Namen zu übernehmen, falls keiner angegeben wurde. `latest_items()` liefert pro Feed die neuesten `MAX_ITEMS_PER_FEED=10` Einträge (Titel/Link/Datum/gekürzte Zusammenfassung), zusammengeführt über alle Feeds, falls keine `feed_id` angegeben ist — die eigentliche Zusammenfassung übernimmt das Chat/Voice-LLM selbst aus diesen Rohdaten, es gibt keinen serverseitigen Zusammenfassungs-Aufruf. `_client()` ausgelagert wie bei `weather_service`/`searxng_service`, rein für `monkeypatch` in Tests. Nutzbar über die Tools `add_rss_feed`/`list_rss_feeds`/`delete_rss_feed`/`list_rss_items` (`app/agent/tools.py`). **Nicht live gegen einen echten Feed getestet** — kein Netzwerkzugriff in der Build-Sandbox dieser Session; Backend-seitig vollständig mit `httpx.MockTransport` und einem eingebetteten Beispiel-Feed getestet (`tests/test_rss.py`). Vor Produktiveinsatz einmal mit einem echten Feed durchklicken.
- `app/services/weather_service.py` — **Wetter**: `GET /weather?location=...` über [Open-Meteo](https://open-meteo.com/) (kostenlos, kein API-Key). Kein DB-Modell, kein Zustand — jede Anfrage geht live gegen Open-Meteos Geocoding-API (Ortsname → Koordinaten) und dann die Forecast-API (aktuelles Wetter + 3-Tage-Vorhersage). Numerische WMO-Wettercodes werden über `_WEATHER_CODES` in kurze deutsche Texte übersetzt (unbekannte Codes fallen auf `"Unbekannt"` zurück statt zu scheitern). `_client()` ist als eigene Factory-Funktion ausgelagert (wie `home_assistant_service._client`), rein damit Tests sie per `monkeypatch` gegen `httpx.MockTransport` austauschen können. **Nicht live gegen die echte Open-Meteo-API getestet** — kein Netzwerkzugriff in der Build-Sandbox dieser Session (per Live-Test bestätigt: die Sandbox-Egress-Policy lehnt den Aufruf mit `403 Forbidden` ab, was aber immerhin zeigt, dass Fehlerbehandlung bis in die Frontend-`ErrorMessage`-Komponente sauber durchläuft). Vor Produktiveinsatz einmal mit echtem Netzwerkzugriff durchklicken.
- `app/services/scheduler.py` — startet beim App-Start (`lifespan` in `app/main.py`) vier `APScheduler`-Hintergrund-Jobs: `_check_expired_timers` (alle 15s, ruft `push_service.send_push()` für abgelaufene, noch nicht benachrichtigte Timer auf, `Timer.notified`-Flag verhindert Doppel-Push), `_check_birthdays` (täglich um 08:00 Serverzeit, pusht für jeden Kontakt mit `birthday_month`/`birthday_day` == heute, `Contact.last_birthday_push_date` verhindert eine doppelte Erinnerung am selben Tag), `_check_recurring_reminders` (jede Minute, pusht für jede fällige `RecurringReminder`, siehe `reminder_service.py`) und `_check_automations` (alle 30s, pusht kantengetriggert - nur beim Übergang in `trigger_state`, nicht bei jedem Poll währenddessen - für jede aktive `Automation`, siehe `automation_service.py`; ein Nutzer mit nicht verbundener/nicht erreichbarer HA-Instanz wird für diesen Poll übersprungen, ohne die anderen zu blockieren) — proaktive Quellen neben neuen Notification-Suggestions (siehe `notification_service.py`) und Agent-Bus-Nachrichten an `"ownai"`. **Bekannte Grenze**: läuft in-process, pro Worker einmal — bei mehreren Uvicorn-Workern/Replicas würde jeder unabhängig pollen und könnte doppelt pushen; `docker-compose.yml` startet aktuell nur einen Worker, betrifft also (noch) nicht die reale Deployment-Konfiguration dieses Projekts. Ebenfalls bekannte Grenze: keine nutzerspezifische Zeitzone für den Geburtstags- und Erinnerungs-Check, "jetzt"/"heute" ist die Server-Zeitzone.
- Alle Fehler laufen über `app/errors.py` (`APIError`) durch zentrale Exception-Handler in `app/main.py` und liefern exakt `{"error": {"code", "message"}}` wie in `API.md` spezifiziert.

## Migrationen

Erste Migration (`alembic/versions/..._initial_schema.py`) wurde per `alembic revision --autogenerate` aus den Modellen erzeugt und gegen SQLite verifiziert. Für Postgres in Produktion: einfach `DATABASE_URL` auf `postgresql+asyncpg://...` setzen (siehe `.env.example`) und `alembic upgrade head` laufen lassen — keine SQLite-spezifischen Typen im Schema.

## Bekannte Einschränkungen dieses Durchgangs

- Kein echter CalDAV-/Ollama-Server in dieser Session verfügbar — die entsprechenden Codepfade sind durch Unit-Tests mit gemockten Schnittstellen abgedeckt (siehe `tests/`), aber nicht gegen einen echten Server End-to-End getestet. Vor dem produktiven Einsatz einmal gegen deinen echten CalDAV-Account und ein laufendes Ollama testen.
- SSE-Streaming für Chat-Antworten ist bewusst noch nicht implementiert (`stream=true` liefert `501`, siehe `API.md`).
- Wyoming/Whisper (`POST /voice/transcribe`): das Protokoll-Handling (`app/services/whisper_client.py`) läuft in `tests/test_whisper_client.py` echt über TCP gegen einen selbstgebauten Wyoming-Test-Server (inkl. echtem `ffmpeg`-Aufruf) — nicht nur gemockt. Trotzdem einmal gegen deine echte wyoming-whisper-Instanz testen (Sprachqualität, Latenz auf deiner P40 parallel zum LLM, tatsächliche Transkriptionsgüte auf Deutsch).
- Web Push (`app/services/push_service.py`, `web/src/lib/push.ts`): Backend-seitig durch Unit-Tests mit gemocktem `webpush()`-Aufruf abgedeckt; Frontend-seitig lief der Subscribe-Flow live bis zum tatsächlichen `PushManager.subscribe()`-Aufruf (dabei wurde ein echter Bug gefunden und gefixt — fehlendes Warten auf `navigator.serviceWorker.ready`). Der eigentliche Versand über einen echten Push-Dienst (Chrome/FCM, Firefox/Mozilla Autopush) konnte in dieser Sandbox nicht getestet werden (kein Netzwerkzugriff zu deren Infrastruktur). Vor Produktiveinsatz: echte VAPID-Keys generieren (siehe `.env.example`), auf einem echten Gerät "Push-Benachrichtigungen aktivieren" in Settings → Konto klicken und einen Timer ablaufen lassen.
